This is E-commerce order fulfillment (single-store online shop).

This application is the backend for an online shop that lets shoppers browse a product catalog, register an account, place orders, and have those orders paid for automatically, while inventory is reserved and replenished behind the scenes. A shopper looks at what's for sale, creates an account, submits an order for one or more products, and the system takes over from there: it prices the order from the live catalog, sets aside the needed stock, and charges the shopper through a payment gateway.

The primary users are shoppers — browsing products, registering, placing orders, and reviewing their own order history — identified on each authenticated request via a bearer-style user context rather than a visible login flow. A store-operations/merchant role maintains the catalog by adding new products. Behind the scenes, placing an order fires an order-placed event that inventory and payment react to independently: inventory reserves stock for the ordered lines, and payment charges the order total through a gateway abstraction, with stock levels also topped up automatically by a background restock job so popular items don't stay unavailable.

Structurally, the business is organized around five capabilities coordinating through one shared event bus and one underlying data store — a product catalog, customer accounts, order placement/history, inventory reservation and restocking, and payment charging. It reads as a single-store retail operation (one catalog, one set of customers, one order pipeline) rather than a multi-vendor marketplace.

Use cases

Each card is one thing a user of this system can accomplish, the steps it goes through, and the source files that implement it.

Place an order

Shopper

A shopper buys one or more products in a single order; the order is priced from the live catalog, triggers a stock reservation, and is charged through payment.

  1. Shopper submits a PlaceOrderRequest with the desired product line items via POST to the orders endpoint
  2. Order service looks up each product's current price from the catalog (PriceOf)
  3. Order and its order lines are recorded and an order-placed event is published on the shared bus
  4. Inventory's order-placed handler reserves stock for each ordered line
  5. Payment service charges the shopper for the order total via the gateway
handlers.goservice.gomodel.gobus.go

Evidence: orders.PlaceOrder; PlaceOrderRequest/LineItem in orders/model.go; bus.Publish/Subscribe; catalog.PriceOf; inventory.OnOrderPlaced

Pay for an order

Shopper

The shopper's order total is automatically charged through a payment gateway as part of placing the order, completing the purchase.

  1. Order placement triggers a charge request for the order total
  2. Payment service forwards the charge to the payment gateway (Gateway.Charge)
  3. Payment outcome is recorded as a Payment tied to the order
gateway.goservice.gomodel.go

Evidence: payments.Charge (service), gateway.Charge, gateway.NewGateway; Payment model

Have stock reserved automatically when an order is placed

Shopper

When a shopper places an order, the requested quantities are automatically set aside from inventory so the order can be fulfilled without being oversold.

  1. Inventory subscribes to order-placed events on the shared bus
  2. When an order is placed, inventory's OnOrderPlaced handler runs
  3. Inventory reserves the ordered quantity of each product (Reserve) against the StockItem records
model.goservice.gobus.go

Evidence: inventory.OnOrderPlaced, inventory.Reserve, StockItem model; bus.Subscribe

  3. Order service returns all orders tied to that customer (ForCustomer)

Merchant

The store keeps products available by automatically replenishing stock on a recurring schedule, without manual reordering.

  1. A background restock job starts and runs on a recurring interval (StartRestockJob)
  2. Each run replenishes StockItem quantities that have fallen low (Restock)
